## 一、1.8 的包结构：靠记忆写一定出错

这两天在包结构上错了 **五次**，每次表现都不一样，但根因完全一致：**没先读客户端的解析类就动手**。

| 包 | 我写错的 | 客户端要的 | 表现 |
|---|---|---|---|
| 0x29 画 | `varint eid + string + long + byte` | `string + 3×int + float + byte` | 客户端越界崩 |
| 0x0E 展示框 | `data` 之后没跟速度 | `data > 0` 时要再跟 3 个 short | 越界崩 |
| 0x15 相对移动 | 位移用 `short` | 位移是 **byte**（1/32 格） | 断线，报"0x21 多 3 字节" |
| 0x11 经验球 | 用 `Spawn Object` 发 | 有独立包 `0x11` | 先画成石头，再画成船 |
| 槽位 NBT | `chr(10) + Nbt::write()` | `Nbt::write()` 已含根标签头 | 断线，长度 2560 |

### 结论

**写任何包之前，先在 `.cache/mc189/bcy.java` 里找到对应的 `a(xxx)` 处理函数**，把字段类型和顺序抄下来。

反例特别值得记：`Nbt::write(Tag, $name = '')` 的签名里那个 `$name` 参数，就说明它写的是**完整根标签**（type + 名称长度 + 名称）。我又手动补了个 `chr(10)`，字节流变成 `0A 0A 00 00`，客户端把 `0A00` 当成名称长度 2560，直接踢人。

> 教训：调用自己写的序列化函数前，先看它的实现或注释，别只看名字。

## 二、TE 方块（箱子/末影箱）不渲染的真正原因

### 症状

方块数据、存档、发出去的 payload 全都正确，客户端就是不画。

### 排查链路

```
/block -66 63 -36          → 130          服务端有
段 NBT Blocks[4046]        → 130          存档有
payload 线上格式            → id=130 meta=0 发出去的也对
客户端                      → 不画
```

### 结论

1.8 客户端里，箱子/末影箱是 `ENTITYBLOCK_ANIMATED`，靠 `TileEntity` 渲染。**区块编译完之后**再创建 TE，不会自动重绘。

真正的触发条件是两条一起：

```
0x35  让 chunk.getTileEntity(pos, CREATE) 造出 TileEntity
0x23  发一条**状态不同**的方块变更 → 触发 markBlockRangeForRenderUpdate
```

**关键细节**：`World.setBlockState` 第一句是

```java
IBlockState old = chunk.setBlockState(pos, state);
if (old == null) return false;      // 状态没变 → 后面全不执行
```

所以"发一条同状态的方块变更强制刷新"是**空操作**。必须让状态真变：

- 末影箱：`(130<<4)|5` → `(130<<4)|realMeta`（meta 是朝向 2~5，别用 0）
- 箱子：历史上直接换成了书架(47)，是绕路，不是解决

## 三、"物品没了"类问题的通用方法

这两天遇到四次「东西不见了」：末影箱、176 旗帆方块、经验、附魔。

**每次都栽在同一个地方：先改代码，后看数据。**

正确的顺序只有一条：

```
1. 打开存档，确认数据在不在
   └─ 不在 → 查写入
   └─ 在   → 查读取 / 传输 / 显示
2. 还在就加"看门狗"：记录基准状态，每拍比对，一变就记日志（带时间戳）
3. 日志直接点名时间点和槽位，再顺着那个时刻的动作查代码
```

附魔这个问题一共改了八轮，前七轮都在猜：

```
第一轮  以为取出时丢        → 改 clickedStacks
第二轮  以为没存盘          → 改 playerdata（改错了文件，正本是 JSON）
第三轮  以为读取丢          → 改 inventory()
第四轮  以为优先级错        → 改成 JSON 优先
第五~七轮  加探针
第八轮  看门狗 → 一次定位（进服 2.6 秒、槽 40、三字段新数组）
```

**看门狗的代码很简单，值得照抄：**

```php
// 进服时记快照
foreach ($c->inventory as $slot => $it) {
    if (!empty($it['ench'])) $c->enchWatch[$slot] = [...];
}
// 每拍比对，变了就记日志（并顺手补回去）
```

第四轮之前的判断之所以错，是因为我**没有同时看"存档"和"内存"两份数据**——只要对一次，就会立刻发现"存档里有、内存里有、发出去有、读回来没有"。

## 四、掉落物 id 的坑（踩了三次）

```
62   点亮的熔炉   → 会掉出 62（无物品形态）→ 客户端 tick 崩
176  旗帜方块     → 同上
117  酿造台       → 同上
```

**根治方式**：从客户端反编译出真实物品注册表，而不是用"id ≤ 450 且不在黑名单"这种启发式。

```
bjh.java   this.a(zy.X, "名字")    按注册顺序从 256 编号（别名不占号）
           this.a(afi.X, [meta,] "名字")   方块物品，id = 方块 id
```

生成 `src/ItemIds.php`，327 个有效 id。`hasItem()` 直接 `isset()`。

**注意两个解析陷阱**：

```java
ae = (afs)a("chest");                  // 带强制类型转换
this.a(afi.b, ajy.a.a.a(), "stone");   // meta 是表达式不是数字
```

第一次生成时这两种都没匹配上，石头/木板/原木/羊毛全漏了——**如果直接上线，玩家背包里这些物品会被"清洗"掉**。

> 教训：生成数据表后，先拿一组已知值对一遍，再上线。

## 五、配方表：从反编译里提取

`tools/extract_recipes.py` 做了三件事：

```
afi.java  字段 = a("名字")        → 方块字段 → 名字
afh.java  a(id, "名字", ...)      → 名字 → id
bjh.java  注册顺序（从 256 起）     → 物品字段 → id
```

**坑**：`bow` 有 `bow_pulling_0/1/2` 三个别名共用一个字段。按行计数会让物品 id 整体偏 2（木棍变 278，实际 280）。只让"本名"占号才对。

**坑**：分割参数不能用 `re.split(", ")`，`new zx(a, 3)` 里的逗号会被切开。要按括号深度遍历。

结果：100 条有形状 + 4 条无序，`src/RecipeTable.php`。

## 六、附魔台

### 窗口

```
类型      minecraft:enchanting_table
slotCount 必须是 0 —— 和工作台一样是"有 GUI id 的容器"，
          发真实槽位数客户端会走"未知类型 → 退回箱子界面"的兜底分支
槽位      0 物品 / 1 青金石（damage 4）+ 36 背包
```

### 窗口属性（这块最容易搞反）

```java
g[i] = 等级消耗;                  // 发在属性 0~2
h[i] = 附魔id | (等级 << 8);       // 发在属性 4~6，是打包的
```

我先发反了：客户端把"消耗 5"当成"附魔 id 5"，提示显示**水下呼吸**，等级显示 0。

### 附魔 NBT

```
tag.ench = List<Compound{ id: short, lvl: short }>
tag.RepairCost = int
```

槽位序列化时：`short id + byte count + short damage + Nbt::write(compound)`。

**不要**在 `Nbt::write()` 前面再加 `chr(10)` —— 它已经输出根标签头。

## 七、经验系统

```
包      0x1F Set Experience：float 进度 + varint 等级 + varint 总经验
曲线    0~15 每级 17 点，16~30 每级 37，之后每级 62
存盘    cache/xp.json（玩家名 → 总经验）
```

**经验球不能用 `Spawn Object` 发**：type 2 是掉落物（EntityItem），type 1 是船（EntityBoat）。经验球有独立包 **0x11**：

```
varInt eid + int x*32 + int y*32 + int z*32 + short 经验值
```

## 八、读写顺序的两个典型 bug

### 1. 变量用在了读取之前

```php
// 锄地/骨粉两段插在 0x08 处理函数开头
if (in_array($itemId, [290,291,292,293,294]))   // $itemId 还没读！
...
$itemId = $r->readShort();                       // 1208 行才读
```

日志刷了上百条 `Undefined variable $itemId`，但一开始只看了"挖方块"那行，没注意这个警告。

> 教训：**PHP 警告不要跳过**，尤其 `Undefined variable` —— 它往往就是"逻辑不生效"的直接原因。

### 2. 存档读写的"正本"搞错

```
.phpmcs_players.json   服务端自己读写的正本
playerdata/<uuid>.dat  只是给外部工具看的副本
```

但 `inventory()` 曾经**优先读 .dat**，而有附魔的 JSON 被忽略。注释里明明写着"正本是 JSON"。

> 教训：改数据层之前，先确认"哪份是正本"，别改了个没人读的地方。
