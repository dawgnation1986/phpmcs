# Minecraft Java 1.8.9 / Protocol 47：PHP 群系与村庄原版还原开发方案

> 目标：在纯 PHP 8 CLI 服务端中，把现有“能生成不同地形/群系”的系统逐步提升为尽可能接近 Minecraft Java Edition 1.8.9 原版的世界生成系统，并从零加入原版村庄。
>
> 当前项目状态：
> - 服务端：PHP 8，单进程 `stream_select`，手写协议编解码。
> - 存档：Anvil `.mca`，直接读写区块 NBT。
> - 群系/地形：已有生成能力，但尚未证明与 1.8.9 原版 GenLayer、地形噪声、装饰器完全一致。
> - 村庄：尚未实现。
> - 目标：优先原版 1.8.9，不加入 1.10+ 村庄、不加入现代 POI/床/铃铛职业系统，也不默认加入温度伤害、口渴等自定义生存规则。

---

## 0. 总体决策：保留现有地形，先建立原版对照，不要直接推翻重写

你们当前已经能生成地形和群系，所以第一阶段不是立刻重写 `ChunkProvider`，而是先回答三个问题：

1. **群系图是否由原版 1.8.9 GenLayer 算法生成？** 还是由 PHP 随机/噪声近似生成？
2. **地形高度和地表替换是否与群系数据一致？** 例如沙漠群系是否真的由沙/砂岩地表规则处理，而不是仅修改草地颜色。
3. **已生成区块是否持久化群系数据？** 重启后是否读取保存的 `Biomes[256]`，而不是重新随机计算？

### 必须先做的兼容性决定

- 备份整个世界目录。
- 对现有世界写入 `worldgen_version`，例如 `phpmc-worldgen-v1`。
- 不要对已经存在的区块自动重新生成；新算法先只作用于**尚未生成的区块**。
- 若以后要升级旧区块，必须提供单独的离线迁移命令，不能在玩家进服时偷偷重建。
- 保存 `seed`、世界类型、生成器配置、群系算法版本、结构算法版本。
- 同一世界的生成配置在世界创建后应锁定；修改配置要创建新世界或显式迁移。

原因：群系/地形算法一旦改变，同一 Seed 的新旧区块会出现边界断层；旧区块与新算法混用时，村庄候选点也可能发生偏移。

- 同一个 Chunk 连续生成两次，输出必须逐字节一致。

- 测试正坐标、负坐标、跨 Chunk 边界。
- 生成后重启服务器，读取到的群系数组必须不变。
- 玩家移动离开再回来，区块不得重新随机生成。

# 3. 第二阶段 P1：建立完整 1.8.9 Biome Registry

## 3.1 不要只存“群系 ID + 名称”

群系定义应当数据化。每个群系至少需要：

```json
{
  "id": 1,
  "name": "Plains",
  "baseBiomeId": 1,
  "isMutated": false,
  "temperature": 0.8,
  "rainfall": 0.4,
  "enableSnow": false,
  "enableRain": true,
  "height": {
    "root": 0.125,
    "variation": 0.05
  },
  "surface": {
    "topState":  "minecraft:grass",
    "fillerState": "minecraft:dirt"
  },
  "spawnLists": {
    "monster": [],
    "creature": [],
    "waterCreature": [],
    "ambient": []
  },
  "decorator": {
    "treesPerChunk": 0,
    "flowersPerChunk": 0,
    "grassPerChunk": 0
  }
}
```

上面只是字段结构示例，具体数值必须从 MCP 1.8.9 `BiomeGenBase` 和各子类提取，不要直接照抄示例里的占位值。

## 3.2 数据范围

至少覆盖原版 Overworld 中实际注册的基础群系和变种群系（Mutated / M 群系）。不要只列常见 10 个群系。

基础群系与变种群系的关系应明确保存：

- `baseBiomeId`：变种所继承的基础群系。
- 地形高度偏移。
- 温度与降雨量继承/覆盖。
- 地表方块继承/覆盖。
- 生物生成列表继承/覆盖。
- 装饰器使用基础群系还是变种群系行为。

群系 ID 是无符号字节语义；写入 NBT / 协议时必须保留 0..255，不能因 PHP `chr()` 或有符号字节处理把大于 127 的 ID 变成错误值。

## 3.3 256 字节 Biomes 数组

Minecraft 1.8.9 的 Chunk 保存 256 个 X/Z 群系值，一个垂直柱子对应一个群系值，不是每个 Y 层单独保存。

索引：

```php
$index = (($localZ & 15) << 4) | ($localX & 15);
$chunk['biomes'][$index] = chr($biomeId & 0xFF);
```

需要注意：

- `localX = blockX & 15`。
- `localZ = blockZ & 15`。
- 索引是 `z * 16 + x`，不是 `x * 16 + z`。
- NBT 中保存 `Level.Biomes` 的 256 字节数组。
- `S21 groundUp=true` 的 Chunk Data 负载必须带正确的 256 字节 Biomes。
- 已有 Chunk 读取存档时应加载 Biomes；只有真正新生成的 Chunk 才调用 BiomeProvider。

**验收：** 将同一 Chunk 的 Biomes 保存、重启、读取、再次发送，256 字节必须一致。

# 4. 第三阶段 P1：把群系分配算法提升到原版 GenLayer

如果当前群系只是在噪声图上随机选 ID，这一阶段才是“地理分布原版化”的核心。

## 4.1 重点源码

从 1.8.9 MCP `GenLayer.initializeAllBiomeGenerators()` 入手，按源码重建整条 Layer 链，而不是单独实现 `GenLayerBiome` 后就认为完成。

重点类包括但不限于：

- `GenLayer`
- `GenLayerIsland`
- `GenLayerFuzzyZoom`
- `GenLayerZoom`
- `GenLayerAddIsland`
- `GenLayerRemoveTooMuchOcean`
- `GenLayerAddSnow`
- `GenLayerEdge`
- `GenLayerBiome`
- `GenLayerHills`
- `GenLayerRareBiome`
- `GenLayerShore`
- `GenLayerRiverInit`
- `GenLayerRiver`
- `GenLayerSmooth`
- `GenLayerRiverMix`
- `GenLayerVoronoiZoom`

实际链条必须以 1.8.9 `GenLayer.java` 的 `initializeAllBiomeGenerators()` 为准；不要拿 1.7、1.12 或现代版本算法拼接。

## 4.2 Java Random 是关键

GenLayer 的随机算法不是 PHP `mt_rand()`。

需要还原：

- `baseSeed` 初始化。
- `worldGenSeed` 递归混合。
- `chunkSeed` 与格子坐标混合。
- Java 64 位 long 的溢出语义。
- `nextInt(bound)` 的行为。
- 负坐标取整与位运算。

Windows PHP 64 位环境尤其要小心：大于 `PHP_INT_MAX` 的整数乘法可能转成 float，不能直接用普通 PHP 乘法假装 Java `long`。建议实现独立 `JavaLong` / 48-bit LCG 辅助类，或用两个 32-bit 无符号字表示并明确测试溢出。

## 4.3 两种分辨率要分清

`WorldChunkManager` 相关链通常存在不同用途的输出：

- 生物群系高分辨率数据（用于 Chunk 内 16×16 Biomes）。
- Voronoi 放大后的群系数据（用于按方块坐标查询、结构位置合法性等）。

不要把“一个 Chunk 的 256 个 biome 值”和“按世界方块坐标查询的最终 Voronoi 群系”混成一个接口。

建议接口：

```php
interface BiomeProviderInterface
{
    public function getBiomesForChunk(int $chunkX, int $chunkZ): array; // 256 IDs
    public function getBiomeAtBlock(int $blockX, int $blockZ): int;
    public function areBiomesViable(
        int $centerX,
        int $centerZ,
        int $radius,
        array $allowedBiomeIds
    ): bool;
}
```

## 4.4 P1 验收

- 同一个 Seed、同一坐标，PHP 输出与 Java/MCP Oracle 完全一致。
- 测试至少 5 个 Seed，包括正负混合的大整数 Seed。
- 测试 Chunk 坐标 `(-1,0)`、`(0,-1)`、`(-1,-1)`、`(1,1)`。
- 比较至少 64×64 Chunk 的群系地图摘要；最终应做逐格比较，不只看图片“差不多”。
- `getBiomesForChunk()` 与 `getBiomeAtBlock()` 在边界处必须一致。

# 5. 第四阶段 P2：群系与地形生成真正联动

你们现在已有地形生成，这一阶段重点是让每根地表柱子正确使用它所属的群系。

建议明确生成阶段：

1. 基础地形密度/噪声生成（石头、空气、水等）。
2. 洞穴、峡谷等地形 carve（如果当前项目已实现则保持原逻辑）。
3. 获取该 Chunk 的 16×16 Biomes。
4. 对每根 X/Z 柱子执行群系地表替换。
5. 处理海平面、海滩、河岸、冰雪等群系专属表面规则。
6. Chunk 基础数据完成后，进入 Populate 阶段生成矿物、树木、植物、装饰物和结构。
7. 保存方块、光照、Biomes、实体、Tile Entity 及生成标记。

## 5.1 地表替换不要只按 biome ID 写 if/else

参考 `ChunkProviderGenerate.replaceBlocksForBiome()` 与 `BiomeGenBase.genTerrainBlocks()`。建议把表面规则放进 `BiomeDefinition` / `BiomeSurfaceReplacer`。

至少区分：

- `topBlock`：最上层表面材料。
- `fillerBlock`：其下方填充材料。
- 海底、海岸、河床。
- 沙漠沙层及砂岩替换。
- 雪原/寒冷群系表面的雪与冰规则。
- 恶地/台地群系的彩色陶瓦层（Mesa 专属地层不能简化成普通草地替换）。
- 蘑菇岛的菌丝表面。

地表替换应依据地形噪声和深度逻辑，不要粗暴地把整张 Chunk 所有草方块全部替换。

## 5.2 Decorator 必须按群系执行

`BiomeDecorator` 负责大量群系装饰，但矿物、树木、植物不能混成一个完全无差别的随机循环。

将装饰项目拆成数据与生成器：

- 矿石生成器。
- 树木生成器（普通树、橡树、云杉、白桦、丛林树、深色橡树、金合欢等）。
- 草、花、蕨类、枯萎灌木。
- 甘蔗、仙人掌、睡莲、蘑菇。
- 南瓜等特殊装饰。
- 海洋/河流相关生成。

每个 Decorator 条目需要明确：尝试次数、坐标随机方式、地面条件、生成器类型、额外随机调用次数。

**原版兼容最重要的是随机数调用顺序。** 即使最终生成物数量相近，如果每个装饰器使用的 Random seed 或 `nextInt()` 调用顺序不同，同 Seed 的生成结果也不会与原版一致。

## 5.3 Populate 的幂等与跨区块规则

- 同一个 Chunk 的 Populate 只能成功提交一次。
- 使用 `populationStarted` / `populationDone` 状态，崩溃恢复时有明确策略。
- 装饰器可能在当前 Chunk 边缘放置方块，因此要有邻区块读取/写入策略。
- 不能因为区块加载顺序不同而多次生成同一棵树或同一片矿脉。
- 若当前没有同步生成相邻 Chunk 的能力，采用待处理写入队列，并将任务与目标 Chunk 绑定、持久化。

# 6. 第五阶段 P2：群系气候与自然生成

目标是原版生态，不是给玩家增加温度伤害。

## 6.1 气候规则

每个群系读取原版属性：

- Temperature。
- Rainfall。
- EnableRain / EnableSnow。
- 高度相关温度修正。

实现：

- 天气是否允许下雨/下雪。
- 温度符合条件时雨变雪。
- 地表积雪与水源结冰的原版条件。
- 草、树叶、天空颜色由客户端按 Biome ID 和原版客户端规则处理；服务端重点保证 Biomes 数据正确。

1.8.9 原版没有现代生存游戏那种“沙漠中暑/雪地冻伤”机制。默认 vanilla 目标下不要添加。

## 6.2 生物生成读取群系 Spawn List

把群系生物生成列表分为原版类别：

- MONSTER。
- CREATURE。
- WATER_CREATURE。
- AMBIENT。
- CAVE_CREATURE（对应原版洞穴生物类别）。

每条记录至少有：

```json
{
  "entity": "Sheep",
  "weight": 12,
  "minGroup": 4,
  "maxGroup": 4
}
```

数值为示例，实际应从每个 1.8.9 群系类及其父类提取。

生成流程至少检查：

- 当前群系列表中是否有该实体。
- 生物类别的全局数量上限。
- 方块支撑、碰撞箱空间、亮度/液体条件。
- 玩家距离与生成区域。
- 群系生成概率。
- 群组数量与权重。

不要使用“全世界共用一张动物表”的方式，否则森林、沙漠、海洋都会出现不符合原版的生物组合。

# 7. 第六阶段 P1：开始实现村庄选址（先不生成建筑）

村庄从这一步开始。**不要第一天就写房子、村民 AI 和交易。** 先把候选村庄 Chunk 算对。

## 7.1 1.8.9 原版 MapGenVillage 的关键常量

原版 1.8.9 `MapGenVillage`：

- 默认区域间隔：32 Chunk。
- 最小分离参数：8 Chunk。
- 候选偏移范围：`nextInt(32 - 8)`，即 0..23。
- 种子盐值：`10387312`。
- 允许群系：Plains（1）、Desert（2）、Savanna（35）。
- 普通世界默认 size/terrainType 为 0。

重要：不要套用 1.10+ 或更新版本的村庄群系列表。1.8.9 原版候选只允许 Plains、Desert、Savanna。

## 7.2 候选 Chunk 的核心算法

忠实翻译 MCP `MapGenVillage.canSpawnStructureAtCoords()`：

```text
input: chunkX, chunkZ

保存原始输入 i=chunkX, j=chunkZ

如果 chunkX < 0:
    chunkX -= spacing - 1
如果 chunkZ < 0:
    chunkZ -= spacing - 1

regionX = chunkX / spacing
regionZ = chunkZ / spacing

random = world.setRandomSeed(regionX, regionZ, 10387312)

candidateX = regionX * spacing + random.nextInt(spacing - separation)
candidateZ = regionZ * spacing + random.nextInt(spacing - separation)

只有原始 chunkX/chunkZ 与 candidateX/candidateZ 完全相等时，才继续检查群系。

检查世界方块位置：
    centerX = chunkX * 16 + 8
    centerZ = chunkZ * 16 + 8

调用 areBiomesViable(centerX, centerZ, 0,
    [Plains, Desert, Savanna])
```

PHP 注意：

- PHP `intdiv()` 对负数是向 0 截断；Java 代码先对负数减去 `spacing-1`，再做整数除法。不要删掉这个负数修正。
- `world.setRandomSeed()` 必须还原 Java 1.8.9 的随机算法和 64 位溢出。
- `areBiomesViable()` 必须使用与原版相同的群系查询分辨率，不能简单查一个未经 Voronoi 的粗分辨率数组。
- 不要使用 PHP `mt_rand()`。

## 7.3 增加诊断命令

```text
/village candidate <chunkX> <chunkZ>
/village locate <blockX> <blockZ> <maxRegions>
/village list
```

`candidate` 输出：

```text
inputChunk=(-14, 2)
region=(-1, 0)
spacing=32
separation=8
seedSalt=10387312
candidateChunk=(...,...)
centerBlock=(...,...)
centerBiome=...
allowedBiome=true/false
result=true/false
```

## 7.4 P1 验收标准

- 同 Seed 同候选 Chunk 结果永远一致。
- 测试正坐标、负坐标和 32 Chunk 区域边界。
- 用 Java/MCP Oracle 对比候选 Chunk 坐标。
- 不能在 Desert / Plains / Savanna 之外生成候选村庄。
- 候选判定只决定“有无村庄起点”，不意味着立刻生成了有效村庄。

# 8. 第七阶段 P2：村庄结构系统

原版村庄不是几栋固定房屋。1.8.9 使用 `MapGenVillage`、`StructureVillagePieces`、`StructureStart`、`StructureComponent` 等组件系统。

## 8.1 组件生成流程

```text
MapGenVillage candidate
    ↓
create Village StructureStart
    ↓
create weighted PieceWeight list
    ↓
create central Start component
    ↓
build initial roads/components
    ↓
process pending roads and pending pieces
    ↓
resolve component bounding boxes
    ↓
calculate village bounding box
    ↓
for each intersecting chunk:
    clip generation to that 16x16 chunk
    write only blocks in that chunk
    persist generated-chunk marker
```

组件选择与扩展必须使用一个稳定的 Java-compatible Random 流；不要每栋房屋用一个随机 seed 独立抽样，否则结果不会接近原版。

## 8.2 第一个可运行版本的实现范围

开发上可以分两步，但最终目标仍然是完整 1.8.9：

**V1 最小闭环：**

- 村庄中心起点。
- 一段道路。
- 至少 3 个非道路组件，才能形成原版有效村庄判定。
- 普通住宅、农田、水井中的一部分。
- 结构跨 Chunk 切片写入。
- 保存结构起点与已生成 Chunk 标记。

**V2 原版组件覆盖：**

- 把 MCP `StructureVillagePieces.java` 中注册的所有 1.8.9 组件类型逐一移植。
- 包含不同群系村庄的材料风格（平原、沙漠、热带草原）。
- 建筑方向、地形高度、道路连接、组件权重、建筑变体和随机装饰。
- 铁匠铺箱子战利品等需要单独实现的内容。

不要把 V1 的少量建筑声称为“完整原版村庄”。

## 8.3 建筑放置 API

所有组件只调用统一接口：

```php
$writer->setBlockState($worldX, $worldY, $worldZ, $state);
$writer->setMetadata(...);
$writer->placeDoor(...);
$writer->placeChestWithLoot(...);
$writer->placeTorch(...);
$writer->placeEntity(...);
```

写入器必须支持：

- 当前目标 Chunk 边界裁剪。
- 负坐标。
- 方块方向 Metadata 转换。
- 结构放置期间抑制不必要的中间邻居更新，结构完成后统一刷新边界。
- Chest / Sign 等 Tile Entity 的 NBT 创建与持久化。
- 对同一 StructureStart + Chunk 的重复调用保持幂等。

## 8.4 跨 Chunk 生成

每座村庄只生成一份全局组件列表和 Bounding Box。生成某个 Chunk 时：

1. 查询与 Chunk 的 16×16 X/Z 范围相交的组件。
2. 组件用 BoundingBox 裁剪，只写入目标 Chunk 范围。
3. 写完后记录该 Chunk 已应用该 StructureStart。
4. 其他 Chunk 加载时对相同组件重复计算，但只写它自己的区域。
5. 不允许根据当前 Chunk 临时随机决定房屋位置。

结构是否已生成、组件数据是否已保存，必须可在崩溃后恢复。

# 9. 第八阶段 P3：村庄持久化

原版 `MapGenStructure` 会把结构起点/组件信息写入 `MapGenStructureData`（WorldSavedData，结构名 `Village`），以便重启后读取已有 StructureStart。

PHP 可以用自己的格式实现，但语义必须相同：

```json
{
  "format": 1,
  "worldSeed": "<exact signed seed string>",
  "structureType": "Village",
  "starts": [
    {
      "chunkX": 12,
      "chunkZ": -9,
      "valid": true,
      "boundingBox": [194, 62, -142, 258, 78, -78],
      "components": [],
      "generatedChunks": ["12,-9", "12,-8"]
    }
  ]
}
```

存储要求：

- 不要把 64 位 Seed 当 JSON 浮点数；使用十进制字符串或二进制 NBT Long。
- 保存版本号。
- 先写临时文件，再原子替换，防止服务端中断造成半个 JSON。
- `generatedChunks` 应使用集合语义，防止重复组件写入。
- 对世界 Seed 和 worldgen 版本做校验；不匹配则拒绝自动加载或要求迁移。

文件建议：

```text
world/data/village_structures.json
world/data/village_manager.json
```

或者实现与原版类似的 WorldSavedData NBT 文件。

# 10. 第九阶段 P3：村民与村庄生态（建筑稳定后再做）

建筑生成和村民 AI 必须分开。先确保建筑、门、农田等在重启后不变，再加入活体实体。

建议顺序：

1. Village Entity Spawn：在对应建筑组件中生成初始村民。
2. Villager Persistence：保存实体 UUID、职业、年龄、位置、交易数据。
3. Basic Villager AI：村庄范围内移动、避障、回家、逃跑。
4. Door / Village Collection：扫描并维护可识别的木门信息。
5. Village Population：按原版节奏统计村民。
6. Villager Trade：交易配方、使用次数、锁定状态、协议窗口。
7. Iron Golem：按原版村庄统计条件和尝试机制生成。
8. Village Siege：最后再实现夜间僵尸围城。

## 10.1 1.8.9 和现代版本的差异

1.8.9 的村庄核心是 `Village` / `VillageCollection` / 木门信息，不是 1.14+ 的 POI、床、铃铛、工作站系统。

不要照搬新版本村民职业站点、村民睡床、袭击队长/袭击等机制。

## 10.2 铁傀儡规则

原版 1.8.9 `Village.tick()` 会定期更新村民与铁傀儡计数；生成条件与有效村庄门数量、村民数和随机尝试相关。MCP 源码中可以看到门数量大于 20、铁傀儡数量低于 `villagers / 10`、每 Tick `nextInt(7000) == 0` 的尝试逻辑。

这段逻辑需要在村庄数据、实体数量统计与随机数都可靠后再启用，不要先写成“每 5 分钟生成一只”。

# 11. 第十阶段：与 PHP 区块/协议系统集成

生成器是服务端内部逻辑；客户端只接收区块和实体结果。不要把“客户端能看到”当成“生成系统正确”的唯一标准。

## 11.1 Chunk 出站前检查

对于每个新生成 Chunk：

- 方块状态数组完整。
- `Biomes` 是 256 个正确 ID。
- 区块 NBT 中有结构放置后的最终方块。
- 有需要的 Tile Entity 已保存。
- 光照数据符合当前服务端策略。
- `S21 groundUp=true` 的序列化包含正确的 Biomes 字节。

## 11.2 结构生成后更新

- 新区块首次发送前，优先先完成生成/Populate/结构放置，再发送完整区块。
- 若结构是在客户端已经加载后才写入，使用对应的方块/多方块更新包，并触发服务端自己的光照、邻居、Tile Entity 更新流程。
- 村庄结构生成期间应避免对每个 setBlockState 都触发昂贵的全局扫描；使用批量写入和边界更新。
- 不要通过每次重发整个 Chunk 来掩盖结构写入流程错误。

# 12. 自动化测试矩阵

| Decorator 幂等 | populate 两次 | 不重复生成 |

# 14. 不要让 AI 编程助手犯的错误

把以下约束写进每次开发提示词：

1. 不允许调用 Bukkit / Spigot / Paper API；项目是纯 PHP 服务端。
2. 不允许把 Java 代码直接当作 PHP 运行；只翻译算法和数据结构。
3. 不允许用 `mt_rand()` 替代 Java Random。
4. 不允许使用 1.10+ 或现代版本村庄、生物群系、POI 机制。
5. 不允许只生成“外观像村庄”的随机房子；必须有确定性 StructureStart 和跨区块组件。
6. 不允许对已有 Chunk 自动重新生成地形或群系。
7. 不允许每次登录重新随机群系、重新 Populate 或重复生成结构。
8. 不允许遗漏 `Level.Biomes` 的 256 字节持久化和 `S21 groundUp=true` 群系数据。
9. 不允许结构跨 Chunk 时只处理当前 Chunk 的中心部分。
10. 不允许把所有群系共用一张生物生成表。
11. 不允许在 vanilla 模式加入玩家中暑、冻伤、口渴等自定义生存规则。
12. 每次修改必须附测试 Seed、坐标、生成前后摘要和回归结果。
