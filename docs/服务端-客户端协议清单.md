# 服务端发包清单（协议 47 / MC 1.8.9）

这份文档是给**改 web 客户端**的人看的。目标：让任何实现了 1.8.9 协议栈的客户端
（mineflayer + prismarine-viewer、flying-squid 的 web 端、eaglercraft 之类）
能接上这个 PHP 服务端并正常显示。

不是协议规范翻译，是**「我们实际发了什么 + 哪里和原版不一样」**。

- 服务端：`D:\codextest\bigfish\phpmcs`，PHP 8，单进程
- 协议号：47（1.8.9）
- 传输：普通 TCP `25565`，或 WebSocket（`ws://` 同端口自动识别，`wss://` 走 `24443`）
- 三个维度**不靠传送门包切换**，靠**世界坐标带**（见第 5 节）

---

## 1. 连接流程

```
C->S  0x00 Handshake   proto=47
C->S  0x00 Login Start  name=<username>
S->C  0x02 Login Success  uuid(string, 带横杠) + name(string)
S->C  0x01 Join Game
S->C  0x39 Abilities
S->C  0x06 Update Health        ← 进服必须发，否则客户端一直显示默认 20/20
S->C  0x1F Set Experience
S->C  0x05 Spawn Position
S->C  0x08 Position And Look
S->C  0x38 Player List Item ×N  (action=0，其他在线玩家)
S->C  0x03 Time Update
S->C  0x21 Chunk Data ×N        ← 每拍 4~8 个慢慢发，不会一口气推 3.7MB
（1 秒后）
S->C  0x38 Player List Item ×N  +  0x0C Spawn Player ×N
```

**1 秒后的那一批是必须的**，原因见第 5 节「Tab 必须先到」。

## 2. 基础包

### 0x01 Join Game

| 字段 | 类型 | 我们的值 |
|---|---|---|
| Entity ID | int | 玩家 eid |
| Gamemode | ubyte | 0 生存 / 1 创造 |
| Dimension | **byte** | **固定写 0**，靠后面的 0x07 纠正（见坑 5.1） |
| Difficulty | ubyte | 0 和平 |
| Max Players | ubyte | 20 |
| Level Type | string | `default` |
| Reduced Debug Info | bool | false |

### 0x03 Time Update

```
long worldAge
long timeOfDay     // 负数表示当天不再流逝
```

### 0x05 Spawn Position

```
position  // 8 字节：x(26bit) y(12bit) z(26bit)
```

### 0x06 Update Health

```
float health
varint food
float saturation
```

### 0x07 Respawn（切维度）

```
int   dimension    // 0 主世界 / -1 地狱 / 1 末地
ubyte difficulty
ubyte gamemode
string levelType   // "default"
```

**客户端收到这个包会把整个世界丢掉重建**。所以服务端在发完它之后会：
清 `sentChunks` → 重发 `0x08` 位置 → 重新排队发区块。

### 0x08 Position And Look

```
double x, y, z
float  yaw, pitch
byte   flags       // 0 = 全部用包里的值
```

### 0x1F Set Experience

```
float  xpBar      // 0..1
varint level
varint totalXp
```

### 0x39 Abilities

```
ubyte flags        // bit0 无敌 bit1 可飞 bit2 飞行中 bit3 创造
float flyingSpeed  // 0.05
float walkSpeed    // 0.1（1.8 这里是 FOV 修正，原版固定 0.1）
```

### 0x02 Chat

```
string json        // {"text":"...","color":"..."}
byte   position    // 0 聊天框 1 系统 2 快捷栏上方
```

### 0x40 Disconnect

```
string json
```

## 3. 区块

### 0x21 Chunk Data

```
int    chunkX
int    chunkZ
bool   groundUp            // 一直是 true
ushort primaryBitMask      // 哪些 section 有数据
varint dataSize            // 后面 data 的字节数
byte[] data
```

`data` 按 section 顺序拼接，每个 section 依次是：

```
4096 字节  Blocks
2048 字节  Data       // meta，nibble
2048 字节  BlockLight // nibble
2048 字节  SkyLight   // nibble（地狱/末地填 0xFF）
```

最后接：

```
256 字节   Biomes     // 主世界是真实群系，地狱全 8，末地全 9
```

**注意**：`primaryBitMask` 为 0 的 section 不写任何数据（连光照都不写）。

**坑**：主世界 128 格高发 8 个 section；地狱也是 8 个（虽然只用了 0..127）。
末地 8 个。客户端对没发的 section 保留 null，不要自己补。

## 4. 实体

### 4.0 DataWatcher 编码（**最重要的一条**）

1.8 是：

```
字节 = (type << 5) | (index & 0x1F)
```

**1.7 才是 `(index << 5) | type`，两者相反。** 搞反的后果是客户端按错误的
类型读数据，直接 `IndexOutOfBoundsException` 断线。

常用条目：

| index | type | 含义 | 字节 |
|---|---|---|---|
| 0 | 0 (byte) | 实体 flags | `0x00` |
| 6 | 3 (float) | 生命值（**末影龙血条靠它**） | `0x66` |
| 2 | 4 (string) | 自定义名字 | `0x44` |

**结束符是 `0x7F`。**

**坑**：`sendMobSpawn` 里那组 `0x00 0x00` 是 index 0 / type 0 / 值 0，
在两种编码下都一样，所以照着它抄容易看不出来。**别在一个包里同时写
`0x00` 和带 type 的条目然后照抄顺序**——写之前先算一遍字节数。

### 0x0C Spawn Player

```
varint eid
uuid   16 字节
int    x, y, z        // 坐标 ×32
byte   yaw, pitch
short  currentItem    // 0 = 空手
metadata
```

**这个包不带名字，也不带皮肤。**

客户端要拿 `uuid` 去 `0x38 Player List` 里查 `GameProfile`。
查不到就得到 `GameProfile(uuid, null)` —— **头顶没名字、默认 Steve 皮肤**。

### 0x0F Spawn Mob

```
varint eid
byte   type            // 63 = 末影龙，58 = 末影人，54 = 僵尸…
int    x, y, z         // ×32
byte   yaw, pitch, headPitch
short  vx, vy, vz
metadata
```

末影龙只有**一个 eid**，客户端自己会画七个身体部件，
部件的 eid 是 `本体 eid + 1..+7`。

### 0x0E Spawn Object

```
varint eid
byte   type            // 2 = 掉落物，51 = 末影水晶
int    x, y, z         // ×32
byte   pitch, yaw
int    data            // 物体专属；掉落物这里是速度，水晶填 0
```

### 0x13 Destroy Entities

```
varint count
varint eid × count
```

### 0x18 Entity Teleport

```
varint eid
int    x, y, z       // ×32
byte   yaw, pitch
bool   onGround
```

### 0x1C Entity Metadata

```
varint eid
metadata
```

### 0x1A Entity Status

```
int  eid             // 注意是 int，不是 varint
byte status          // 2 = 受伤（闪红 + 播受伤音效），3 = 死亡
```

### 0x12 Entity Velocity

```
varint eid
short  vx, vy, vz    // 单位是 1/8000 格每 tick
```

### 0x1B Attach Entity

```
int  eid             // 骑乘者
int  vehicleId       // -1 = 下来
byte leash
```

### 0x11 Spawn Experience Orb

```
varint eid
int    x, y, z       // ×32
short  amount
```

### 0x29 Explosion

```
float x, y, z
float radius
int   recordCount
byte  dx, dy, dz × recordCount
float playerMotionX, Y, Z
```

我们发的时候 `recordCount = 0`（只做视觉，不真的炸方块）。

### 0x29 Sound Effect —— **和服务端现有实现冲突，见坑 5.3**

```
string soundName
int    x, y, z       // ×8
float  volume
float  pitch
```

## 5. 已知坑（改客户端前必读）

### 5.1 维度不是靠传送门切的，靠坐标带

服务端把三个维度放在**世界坐标的三个区域**里，不是真的三个世界：

| 维度 | 中心（区块） | 世界坐标 | 半径 |
|---|---|---|---|
| 主世界 | (0, 0) | 0, 0 | — |
| 地狱 | (12500, 12500) | 200000, 200000 | 512 区块 |
| 末地 | (18750, 18750) | 300000, 300000 | 128 区块 |

每 0.5 秒服务端会比对「玩家坐标落在哪个带」和「客户端当前维度」，
不一致就发 `0x07` + `0x08`。

**所以 `Join Game` 里的 Dimension 恒为 0**，进服后靠这一拍纠正。
客户端如果自己缓存了维度，**必须**以 `0x07` 为准。

### 5.2 Tab 必须先到（web 客户端最容易在这里翻车）

mineflayer 的 `named_entity_spawn`（就是 0x0C）里有这么一段：

```js
bot._client.on('named_entity_spawn', (packet) => {
  // in case player_info packet was not sent before named_entity_spawn : ignore
  if (packet.playerUUID in bot.uuidToUsername) {
    创建实体
  }
})
```

`uuidToUsername` 只从 `0x38 Player List Item` 填。

**如果 Tab 还没处理完，这个 Spawn 包会被静默丢掉，而且永不重试。**

服务端的对策：

1. 进服瞬间：只发 `0x38`，**不发** `0x0C`
2. 1 秒后：给本人 `Destroy → 0x38 → 0x0C`，给其他玩家 `0x38 → 0x0C`

**如果自己写 web 客户端**，可以不依赖这个 1 秒延迟，
但必须保证 `0x38` 的 handler 是同步完成的、且在 `0x0C` 之前。

### 5.3 `0x29` 这个 ID 被占用了两次

`src/Server.php` 里同时有：

```php
private const C_SPAWN_PAINTING = 0x29;
private const C_SOUND_EFFECT   = 0x29;
```

按 wiki.vg 的 1.8.9 表，`0x29` 是 Sound Effect，Spawn Painting 应该是 `0x2B`。
**目前发画的地方用的就是 0x29，没验证过**；音效包发出去客户端会按画解析，
报 `found 3 bytes extra` 直接断线，所以音效现在是关掉的。

**改客户端时别按这份常量表去解析 `0x29`**，以实际收到的字段长度判断更保险。

### 5.4 末影龙的七个部位

打龙时客户端发的是 `Use Entity`，`targetEid` 是**部位**的 eid（`本体 + 1..+7`），
不是本体。服务端是按范围判断的：

```php
$targetEid >= $dragon['eid'] && $targetEid <= $dragon['eid'] + 7
```

客户端渲染时不用管这个，但做伤害数字之类的功能要注意。

### 5.5 龙的血条

屏幕顶部那条紫色血条是客户端根据 `EntityDragon` 的 **DataWatcher index 6**
自动画的。服务端只在三种时候发：

- 生成时（`0x0F` 的 metadata 里）
- 受伤时（`0x1C`）
- 每 10 tick 回血（`0x1C`）

**如果没有 `0x1C` 里那个 `0x66` + float，血条不会动。**

### 5.6 Chunk Data 不要一口气发

服务端每拍只发 4~8 个区块。一次推 49 个（约 3.7MB）客户端接不住，
表现是「进去全是石头，放一块方块才啪一下变正常」。

### 5.7 掉落物和物品实体的 NBT

`0x0E`（Spawn Object）之后紧跟一条 `0x1C`（Entity Metadata），
里面 index 10 是物品栈：

```
short itemId
byte  count
short damage
byte  nbtTagCount   // 0 = 没有 NBT
<nbt bytes>         // 有附魔/改名时才有
```

**NBT 标记写死 0 的话，丢出去的附魔装备会变白板。**

## 7. web 客户端适配清单

改之前先对着勾一遍：

- [ ] `0x38` 的 handler 是同步的，且在 `0x0C` 之前完成
- [ ] `0x0C` 收到后按 `uuid` 去 `0x38` 缓存里找 `GameProfile`，找不到也要建实体（否则人隐形）
- [ ] DataWatcher 解码用 `(type << 5) | index`
- [ ] `0x07` 之后清空区块缓存和实体表，等新的 `0x21`
- [ ] `0x21` 的 `primaryBitMask` 为 0 的 section 不要自己补数据
- [ ] `0x0F` type=63 走「末影龙」分支，血条读 index 6
- [ ] `0x1A` 的 eid 是 **int** 不是 varint
- [ ] `0x18` 的坐标是 `×32` 的 int
- [ ] `0x29` 按实际字段长度判断是画还是音效（见 5.3）
- [ ] 掉落物的 `0x1C` metadata 里 index 10 要解析 NBT
